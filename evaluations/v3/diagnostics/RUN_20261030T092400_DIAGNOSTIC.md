## 2. CAND_5 (SQLite WAL): can official document context establish identity?

**Root cause:** for named alternatives, the acceptance rule requires the name or an alias in the excerpt's context window. CAND_5 (sqlite.org/wal.html, "Writers merely append new content to the end of the WAL file…") passed the verifier's identity checks but contains no literal "SQLite" nearby. CAND_3 (docs.python.org sqlite3 module) failed the same way. In substance, both are about SQLite, so the rejections are false.

**A fix was tried and reverted.** It was an "official-source identity" rule: accept when the page is on the alternative's official domain, the domain itself carries the alternative's name, the host is not multi-tenant, and the verifier already confirmed identity. The existing safety test **V04** then failed: an excerpt on VendorY's *own official pricing page* that describes another product (QuuxDB), with a fooled verifier, would have been accepted.

Official pages do quote competitors, and the literal-name check is the backstop against a fooled verifier. A safe version needs a reliable "names another product" detector, which the project does not have. **Answer: not without weakening attribution, so the rule is unchanged.** These are documented false rejections.

## 3. Retrieval: does it prioritise criterion-relevant documentation?

**Not reliably.** The attempt-0 query comes from the shared query builder: alternative name, the criterion **identifier** words, and "official documentation", restricted to the official domain. For `maintenance_responsibilities` that became "SQLite maintenance responsibilities official documentation" on sqlite.org. Exa matched "responsibilities" to legal/governance pages (`consortium_agreement-20071201.html`, `qmplan.html`) instead of operational documentation. The PostgreSQL equivalent happened to hit `maintenance.html`.

The criterion's **description** keywords ("service administration, upgrades, backups, monitoring") are only used at attempt 2.

**Not changed.** The attempt-0 query is shared with the static baseline and frozen in the evaluation protocol. Changing it changes the methodology, so it is recorded as a limitation and a candidate for a future protocol version (description keywords at attempt 0).

## 4. EV_4: does the PostgreSQL backup excerpt justify persistence = 1?

> "As with everything that contains valuable data, PostgreSQL databases should be backed up regularly. While the procedure is essentially simple, it is important to have a clear understanding of the underlying techniques…"

Anchor 1 reads: "Data can persist reliably, but deployment or backup practices require deliberate configuration."
- **Meets** the anchor's *backup* clause: backups need deliberate understanding.
- **Says nothing** about whether PostgreSQL persists data durably across restarts and deployments.

**Verdict:** partially justified. It is a defensible middle score, but it is weak evidence for the persistence criterion as a whole. Because the source is first-party documentation of a non-time-sensitive fact, the cell gets factual confidence "high". That overstates what this one excerpt shows.

**Not changed:** this is the same verifier-judgement limitation as section 1. The recommendation was withheld anyway.

## Residual risks (documented limitations)

1. Verifier strictness and inconsistency on documentation-style excerpts; same model family as the extractor.
2. Literal-name identity causes false rejections of official pages that do not repeat the product name.
3. Attempt-0 queries use criterion identifiers, so retrieval can drift to off-topic pages on official domains.
4. Official first-party evidence can receive "high" factual confidence for claims it only partly supports.

None of these was fixed, to avoid weakening attribution or changing the frozen methodology without a paid validation run.
